# 悬浮标

一个常驻桌面的悬浮工具条，按下快捷键就能把问题送进 ChatGPT 或 Gemini，
**不用切窗口、发完也不被打扰**。也可以一次发给两家，拿回答对着看。

消息送出后，工具条会从胶囊收拢成一个圆环，用圆环表示"对面还在生成"，
生成结束再展开回胶囊。目标应用始终留在后台，不会跳到你面前。

```
待机        生成中        完成         闲置 10 秒
┌────────┐   ╭───╮       ╭───╮
│ ✎ │▱│⌄│ →  │ ◠ │  →    │ ◯ │  →  展开回胶囊  →  ·
└────────┘   ╰───╯       ╰───╯
  胶囊      蓝环转动     绿环闭合         收成小圆
```

闲着超过 10 秒会缩成一个小圆躲开视线，鼠标移上去就展开。
本体以外的透明区域不挡桌面点击。

## 支持的目标

| 目标 | 投递方式 | 进度探测 | 精度 |
|---|---|---|---|
| ChatGPT Classic（桌面端） | 闪切窗口 → 粘贴 → 回车 → 还原焦点 | UIA 可访问性树 | 半精确 |
| ChatGPT（新版桌面端） | 同上 | UIA，失败则降级 | 半精确 |
| Gemini（桌面端） | 同上 | 窗口像素差分 | 粗糙 |
| ChatGPT / Gemini 网页端 | 浏览器扩展直接操作输入框 | 读 DOM 的"停止生成"按钮 | 结束时刻精确 |

## 两个关键取舍

**1. 投递瞬间会短暂切走焦点。**
Windows 的键盘输入只会送给前台窗口，所以把文字送进那两个封闭的桌面应用时，
必须让目标窗口短暂地拿到焦点。整个过程约 200–400ms，结束后焦点立刻还给你原来所在的窗口。
做不到"全程不切窗口"，但能做到"发完不打扰"。

**2. 进度是估算的，不是真进度。**
没有任何一个目标会告诉我们"回复完成了百分之多少"——我们只能知道它**还在不在生成**。
所以圆环默认是转圈（不确定态），绝不显示编造的百分比。
三档探测按可靠性自动降级：

- **UIA**：生成时发送按钮会变成"停止"按钮，轮询可访问性树即可判断。
  实测 ChatGPT Classic 的 a11y 树可以被唤醒（节点数 8 → 245）。
- **像素差分**：抓窗口缩略图比较相邻帧，画面在变 = 还在生成。
  实测 Gemini 桌面端的 a11y 树唤不醒，只能吃这一档。
- **DOM**：网页端由扩展直接读"停止生成"按钮，结束时刻最准。

## 快速开始

```bash
pnpm install
pnpm dev
```

启动后工具条出现在主屏右下角。`Enter` 送出，`Esc` 收起，`Tab` 切换目标，
`/` 找提示词，`Ctrl+Shift+V` 唤出剪贴板历史。
右键托盘图标可以换目标或退出。

唤起输入条的快捷键**不是固定的**：程序会从候选表里逐个尝试，用第一个没被占用的，
**托盘菜单第一项显示的就是当前实际生效的组合**（原因见「踩过的坑」第二条）。

### 提示词按分类检索

内置 82 条，分成八类：学习解题、科研写作、数据分析、编程开发、文字处理、
绘图生成、视频分镜、商业素材。打下 `/` 时提示行会把这八个名字列出来。

搜索认分类名，也认别名——想找画图的提示词，打 `/绘图`、`/画图`、`/插画`、`/image`
都能把整组捞出来。标题命中仍然排在分类命中前面，所以 `/推导` 出来的第一条
一定是那条叫「分步推导」的，而不是整个学习解题分类。

内容是从七个开源 skill 仓库蒸馏来的（nature-skills、scientific-agent-skills、
anthropic-art、photo-abstract-editorial、fal-ai、PixVerse、SenseNova）。
那些 skill 本身依赖 CLI、API key 和多文件路由，搬不进一个对话框；
搬进来的是它们各自真正值钱的那部分——可检验的硬约束。比如「Anthropic 插画」
那条保留了全部八个色值和「承载形占 55%–80%」这类死数字，
因为脱开这些约束，它就只是一句「画得好看点」。

视频那一类要单独说一句：**ChatGPT 和 Gemini 出不了视频**。
那组提示词的产出是分镜表和喂给视频模型的那段描述，拿到之后自己贴进
即梦、可灵之类的工具里。这类工具的成败八成落在描述写得准不准，
而那恰好是对话框帮得上忙的部分。

### 输入条弹在哪儿，取决于怎么唤起

- **点悬浮标上的铅笔** —— 贴着悬浮标弹出，手和视线都不用挪。
- **按全局快捷键 / 托盘菜单** —— 落在屏幕中间偏上，和这类唤起式输入框的通用位置一致。

区分这两种是因为预期本来就不同：热键唤起时鼠标可能在任何地方，没有可跟随的锚点；
而点了右下角的按钮却让输入条飞到屏幕正中，等于让人横跨半个屏幕去找自己刚点出来的东西。

贴着悬浮标时，**展开提示词列表是往上长的**（钉住下边）。
悬浮标常年待在屏幕底部，按常规往下长会一路盖过它再戳出屏幕，
表现为「列表只露出前两条」。日志里会写明钉的是哪条边：

```
[输入条] 贴悬浮标上方 → 1418,798（悬浮标 1808,941 216×113）
[输入条] 调整高度 132 → 380（钉下边，y 800 → 552）
```

### 背景是真的模糊

输入条和目标面板走 Win11 的**亚克力**材质，背后的窗口是真被 DWM 模糊掉的，
不是画上去的渐变——CSS 的 `backdrop-filter` 做不到这件事，
透明窗口背后的桌面根本不在渲染进程的合成范围里，它只能模糊窗口自己的内容。

代价是这条路和 `transparent: true` **互斥**，所以两条路在建窗时就得选定一条：

| | 亚克力 | 伪玻璃（兜底） |
|---|---|---|
| 窗口 | `transparent: false` + `backgroundMaterial` | `transparent: true` |
| 圆角 | 找 DWM 要（只有圆/小圆/不圆三档） | CSS 画，半径随便定 |
| 投影 | 系统给 | CSS 画，窗口四周留 8px 透明边 |
| 底色 | 半透明薄层，透出模糊 | 斜向渐变 + 内高光 |

启动时判一次（Win11 22H2 以上、且用户没关掉「透明效果」），结论写在日志的
`[材质]` 一行里，并经 URL query 传给渲染层——两边必须认同一个结论，
否则会出现「窗口是方角不透明的，CSS 却在里面画圆角卡片」，四角露底。

**悬浮标本体享受不到**：它要不规则形状和鼠标穿透，窗口只能是透明的。
所以它继续是一枚实心胶囊，只是配色和输入条来自同一份 `tokens.css`。

### 送达与完成时的动画

两个时刻会有表示：**话送进去了**（`sending → thinking`）和**对面说完了**
（`thinking → done`）。两者轻重不同——送出去之后你的注意力已经移开，
那一下只需要回答"送到了吗"；完成才是唯一值得把你叫回来的时刻。

**隆重程度跟着探测档位走**，这是"圆环不画假百分比"的同一条原则：

| 档位 | 怎么判定完成 | 给什么 |
|---|---|---|
| `exact`（网页端读 DOM 的停止按钮） | 结束时刻真准 | 撑开窗口，粒子汇聚 + 绿环 + 🎉 + 向外迸散 |
| `approximate`（桌面端 UIA） | 方向可靠，有延迟 | 同样撑窗口，粒子减半，结尾是 ✨ 不是 🎉 |
| `coarse`（像素差分） | 只知道画面一秒多没变 | 只有绿环闭合加一圈涟漪 |

`coarse` 判定"完成"的依据可能只是对面打字停顿了一下。这时候撒花等于
替它宣布"我确定它讲完了"——动画的确信程度不该超过探测的确信程度。

完成时窗口会从 216×110 临时撑到 360×260 再缩回：本体只有 52，
不撑开的话粒子最远只能从 50px 外飞进来，"汇聚"看着像"抖了一下"。
多出来的透明区域不挡桌面点击，命中判断用的一直是本体矩形而不是窗口矩形。

想换 emoji 就改 `pet.ts` 顶部那两行数组，那是这套动画唯一需要调口味的地方。
整套效果可以在托盘菜单里关掉——天天在用的常驻工具，同一段动画看第一百遍
就只剩负担了。系统里开了"减弱动画"时它自动不放，结果态（绿环）照常给。

### 同时发给两家

在目标面板里 **Ctrl+点击**可以把第二个目标也加进来，同一个问题就会同时送往两边，
拿两家的回答对着看。普通点击仍然是「换到它并关闭面板」——最常用的那条路一步没变。

输入条上的目标按钮这时显示 `ChatGPT +1`，面板标题写「同时发给 2 个」。
托盘菜单那边只管单选：点任何一个就是「换成它」，顺带丢掉附加的目标。

圆环按目标数分成几段，每段一轨：

```
两轨都在生成        一轨完成了          都完成了        一成一败
   ╭──╮              ╭──╮              ╭──╮            ╭──╮
  ╭ 蓝 ╮            ╭ 蓝 ╮            ╭ 绿 ╮          ╭ 红 ╮
  ╰ 蓝 ╯            ╰ 绿 ╯            ╰ 绿 ╯          ╰ 绿 ╯
   ╰──╯              ╰──╯              ╰──╯            ╰──╯
```

**每段不各自转圈**，只用颜色表示自己走到哪了，还在跑的那段轻轻呼吸。
两段反着转看着像坏了，而且「谁转得快」会被读成「谁快要好了」——
探测压根给不了这个信息，那就是编造。

庆祝的隆重程度按**所有轨里最低的那一档**算。两家里有一家只能靠像素差分时，
「全都说完了」这个判断整体上就只有像素差分那么可信，不该因为另一家是 `exact` 就升格撒花。
这是「动画的确信程度不该超过探测的确信程度」的直接推论。

> ⚠️ **桌面端的多个目标是排队发的，不是一起发。**
> win32 那条链是「抢前台 → 粘贴 → 回车 → 还原焦点」，两个同时跑会互相抢焦点：
> 第二个把前台夺走时，第一个的 Ctrl+V 正好落进第二个的输入框，
> 于是一条消息发了两遍、另一条一个字都没有。这种事不报错，只是结果莫名其妙。
> 网页端由扩展直接操作 DOM，不碰焦点，所以它们是真并行的。

### 完成之后，点一下就过去了

绿环可以点，点了就把那个目标的窗口带到前台。

「发完不打扰」不等于「不给回去的路」：生成完那一刻你唯一想做的事就是去看它说了什么，
而在这之前那还得自己把窗口找出来。桌面端走 helper 的 `focus`（和输入条抢焦点同一条路），
网页端由扩展 `tabs.update` + `windows.update` 把标签页和浏览器窗口一起提到前面。

同时发给多个目标时**连点会依次轮换**：点一下看这家，再点一下看那家。
圆环只有 52px，分不出可点击的扇区，轮换是这里唯一说得通的交互。

为此 `done` 的停留时间从 4 秒加到了 8 秒。4 秒只够「看见它完成了」；
而这一刻你多半正在别的窗口里打字，抬头、认出绿环、把鼠标挪过去再点，4 秒到不了，
点击入口等于摆设。提示文字只在鼠标压上来时才出现——天天在用的工具，
每次完成都弹一句「点我」，看到第一百遍就只剩噪音。

浏览器窗口那一步可能被系统的前台锁定挡下（和主程序抢前台是同一个机制），
那时最多是任务栏图标闪一下。但标签页已经切对了，所以失败只记日志，不打断你。

### 送不到的话，话会还给你

投递**全都失败**时，输入条会重新弹出来，刚打的那段话原样填在里面，光标停在末尾。

这条路以前是漏的：提交时输入框是立刻清空并隐藏的——那一刻还不知道送没送到；
等知道的时候文本已经不在任何地方了，剪贴板也指望不上，因为投递路径写的那两次
恰好被剪贴板历史的静默窗口排除掉。于是一次「目标应用收在托盘里」就能让人白打一整段，
而那正是〈已知限制〉里明写着会发生的事。

**部分成功不还**。两个目标里送到了一个还把文本弹回来，很容易让人顺手又发一次，
那就变成重复投递了。这时圆环上那一段已经是红的，气泡会说「1 个目标没送到」。

光标放末尾而不是全选：还回来的文本多半是要改一两个字（或者先把目标窗口打开）再发，
全选之后随手一敲就全没了。

### 调试开关

```bash
XFB_DEMO=1 pnpm dev              # 循环播放全部形态（三个探测档位各走一轮），不触发真实投递
XFB_SELFTEST=chatgpt-web pnpm dev # 启动 6 秒后自动投递一条测试消息到指定目标
XFB_SELFTEST=a,b XFB_REVEAL=1 pnpm dev  # 逗号可同时投多个；REVEAL 在完成后自动跳一次目标窗口
XFB_CLIPTEST=1 pnpm dev          # 自检剪贴板的静默窗口，结论直接打在日志里
XFB_FALLBACK=1 pnpm dev          # 强制走伪玻璃，验证亚克力不可用时的那条路
```

`XFB_FALLBACK` 是为了让兜底路径**跑得到**：不然要验它就得去系统设置里
关掉「透明效果」再重启，而那是整台机器的全局设置，改完忘了关回来
所有应用的观感都跟着变。这条路坏掉时不报错，只是圆角和边距全错。

`XFB_DEMO` 用来调形态变换、圆环和庆祝动画。三个档位各走一遍完整的
「送出 → 生成 → 完成」，因为庆祝是**按档位分**隆重程度的，单档演示看不出分档对不对。
最后还会走一轮**双轨**：两轨都在生成 → 一轨先完成（一半绿一半蓝，分段环最值得看的就是这一帧）
→ 都完成 → 一成一败。多轨帧走的是真的 `aggregate`，不是手写的聚合结果——
手写的话演示里一切正常、真实运行时却不是那么回事，而这个开关存在的意义正是把真实形态摆出来看。
`XFB_SELFTEST` 用来验证「投递 → 探测 → 圆环」主链路，绕开快捷键和手动输入——
模拟键盘在焦点和时序上很不稳，会引入与产品无关的噪音。
逗号分隔就能一次验多轨（`XFB_SELFTEST=chatgpt-classic,gemini-desktop`）：
分段圆环、win32 的串行排队、按最低档庆祝，全都只有多目标时才走得到。
它走的是和真实提交**同一条**路径，所以投递失败时一样会把文本还出来——
回填要是只挂在 IPC 那头，「会不会丢文本」就变成了取决于从哪个入口发的。

`XFB_REVEAL=1` 配合前者，在生成完成后自动跳一次目标窗口。
跟 `XFB_CLIPTEST` 是同一个理由：这条路平时只有亲手点绿环才走得到，脚本驱动不了，
而它坏掉时不报错，只是点下去没反应。默认不开：跳转会抢前台，
不该让普通自检顺手把你的窗口抽走。

`XFB_CLIPTEST` 验的是剪贴板历史的静默窗口：**程序自己写进剪贴板的东西不能进历史**。
这条路径平时只有投递和「复制连接密钥」会走到，两者都需要真实的目标应用或一次
托盘点击，脚本驱动不了；而它坏掉时不报错，只是历史里悄悄多出几条你自己发的内容。
自检两个方向都验——静默里写的必须记不下、静默外写的必须记得下，
只验前者的话，一个「什么都不记」的实现也能骗过它。

### 出问题先看日志

主进程日志里这几类前缀是排查的第一手线索：

| 前缀 | 说明 |
|---|---|
| `[快捷键]` | 哪个组合被占用、最终启用了哪个 |
| `[输入条]` | 这次摆在哪、变高时钉的哪条边、焦点的来去 |
| `[投递]` | 这一轮送去了哪个目标 |
| `[剪贴板]` | 记下了什么、为什么跳过某一条、有没有降级 |
| `[探测]` | 选用了哪一档探测（降级与否） |
| `[桥]` | 扩展握手、可用目标、投递结果与网页端进度 |
| `[…渲染层]` | 两个窗口的 console 转发，渲染层报错不再是黑箱 |

这些日志同时落进 `%APPDATA%\XuanFuBiao\logs\`，托盘菜单的「打开日志文件夹」直接开到那儿。

落盘不是为 dev 准备的——终端里本来就看得见。它是为**打包版**准备的：
从开始菜单双击启动时没有终端，stdout 无处可去，上面这些前缀一条也看不到，
而那恰恰是日常真正的启动方式。这个工具的故障又几乎全是「不报错的静默失效」
（下面整节都是），没有日志就等于没有线索。

文件按时间戳命名（`main-20260918-151620.log`），单个满 1MB 就换下一个，
目录里只留最近 3 个。重启会接着最近那个写，所以一个文件里可能有多次启动，
每次开头有一行 `——— 启动 ———` 分隔。

> **日志里只有一行「——— 启动 ———」然后就没了？**
> 那是被**单实例锁**挡下了：已经有一个在跑了（常见情况是 `pnpm dev` 开的那个
> 没退干净，它还占着桥的 47615 端口）。日志落盘装在锁之前，所以启动行照写，
> 后面的一概没有。查法：任务管理器里找 `XuanFuBiao.exe` 和 `electron.exe`，
> 或者 `Get-NetTCPConnection -LocalPort 47615 -State Listen` 看端口在谁手里。

> ⚠️ **轮转刻意不走 `main.log → main.1.log → main.2.log` 那套改名链。**
> Windows 上被 unlink 的文件会先进入 pending-delete，目录项还在，
> 这时往那个名字上 rename 会报 `EXDEV: cross-device link not permitted`——
> 同一个目录里也报。而这条链一旦中途抛异常，日志系统会把自己整个关掉，
> 不留任何痕迹：正是它本来要帮忙排查的那种故障。
> 换成时间戳命名之后，写入路径上只剩「创建」和「追加」，清理旧文件是独立的一步，
> 失败最多是多留几个文件。

## 剪贴板历史

要发给 AI 的东西极少是现打的——是刚复制的一段报错、一段代码、一张截图。
所以后台记着你最近复制过的 **15 条**内容，在输入条里按 `Ctrl+Shift+V` 唤出：

```
Ctrl+Shift+V   打开/关闭列表
↑ ↓ / Tab      选
Enter          取用
Esc            关列表
打字            关列表，字正常进输入框
```

**文本条目插到光标处**，不是整体替换——剪贴板里的东西通常是要贴进一句
已经写了一半的话里的（「这段报错什么意思：<贴在这儿>」）。输入框为空时
光标在 0，效果与填入完全一样。

**图片只能放回剪贴板。** 两条投递链路——win32 那条是「写剪贴板 → Ctrl+V → Enter」，
web 那条是扩展往输入框塞文本——都只吃文本，图片送不进任何目标。
所以选中一张图片时做的是把它写回系统剪贴板，再提示你切到目标窗口自己按 Ctrl+V。
这件事在列表里就写明了，不用等按下 Enter 才发现。

上限只有 15 条是刻意的：这是**喂给 AI 的素材来源**，不是通用剪贴板管理器。
列表要能一眼扫完，而不是变成另一个需要搜索的库，所以也没做置顶收藏和搜索。

### 关于隐私

**不做任何内容过滤：复制了什么就记什么，密码和验证码也一样。**

试过按剪贴板上的「别记录我」标记来跳过，但那玩意儿只是各家密码管理器的约定，
设不设全看它们心情——挡住一部分反而给人一种「已经安全了」的错觉，
比老老实实说「全都记」更危险。所以只留两样实打实的东西：

1. **15 条硬上限**，旧的自动挤掉，图片文件一并删除。
2. **托盘菜单里的「清空剪贴板历史」**，一直摆在明面上，连图片一起清干净。

这是本机自用的工具，历史不出这台机器，也不进任何投递链路——
但它就明文躺在 `userData/clipboard.json` 里（图片原图在 `userData/clips/`），心里要有数。

## 临时篮子

临时篮子复现了 [Tokri](https://github.com/jarusll/tokri) 的核心工作流：拖着文件、文件夹、
文本、链接或图片时，快速左右摇三次鼠标，篮子会在光标附近出现。也可以点悬浮标中间的
篮子按钮，或从托盘菜单打开。

- 拖进来的文件与文件夹会**复制**到 `userData/basket/`，原件保持不动。
- 文本与链接会变成可拖出的 `.txt` 文件；网页直接拖出的内存图片会保存成图片文件。
- 双击打开；右键可以复制、在资源管理器中定位或移到回收站。文本与链接复制内容，
  图片复制图片本身，文件与文件夹可直接粘贴到资源管理器。
- 从篮子里拖到其它程序即可使用；按住 `Ctrl` 可明确要求 Windows 执行复制。
- 关闭窗口不会清空内容，重启后仍在。需要删除时使用右键菜单。

摇动手势只在**按住鼠标左键**时检测，普通移动鼠标不会误触。检测在现有 Windows helper
里用低级鼠标钩子完成；Electron 主进程只读取一次性触发标志，不会记录鼠标轨迹。

该功能基于 Tokri 的交互与摇动检测算法重新实现，Tokri 使用 MIT 许可证；归属与许可证全文
见 [`THIRD_PARTY_NOTICES.md`](./THIRD_PARTY_NOTICES.md)。

## 安装浏览器扩展（网页端才需要）

1. 打开 `chrome://extensions`，开启「开发者模式」
2. 「加载已解压的扩展程序」，选 `apps/extension`
3. 托盘菜单 →「复制扩展连接密钥」
4. 扩展的选项页里粘贴密钥，保存

桥只监听 `127.0.0.1:47615`。因为本机任何网页都能连上本地 WebSocket，
所以必须用密钥确认身份，否则随便一个页面都能驱动你的 AI 客户端发消息。

## 项目结构

```
packages/shared/      状态机、目标定义、桥接协议（两端共用的契约）
apps/desktop/
  src/main/
    orchestrator.ts   状态唯一真源：串起投递与进度跟踪
    win32/            窗口定位、投递
    probe/            三档探测器与降级编排
    clipboard/        剪贴板监视与历史存储
    basket/           临时篮子的磁盘存储与路径边界
    bridge/           与扩展通信的本地 WebSocket 服务
  src/renderer/       胶囊 ⇄ 圆环的形态变换（纯 CSS 动画）
  resources/
    win32-helper.ps1  Windows 能力层
apps/extension/       MV3 扩展，原生 JS，无构建步骤
```

### 为什么 Windows 能力层是一个 PowerShell 脚本

窗口定位、焦点切换、模拟按键、UIA 树查询、全局拖动摇动检测这些能力，用原生 Node 模块要走 node-gyp，
在 Windows 上编译链很脆。而这些能力用 P/Invoke 加 `UIAutomationClient` 全都拿得到，
且零编译依赖。主进程把它当常驻子进程，用 JSON 行协议通信。

> ⚠️ **`win32-helper.ps1` 必须保存为 UTF-8 with BOM。**
> Windows PowerShell 5.1 读取无 BOM 的 UTF-8 脚本时会按系统 ANSI 代码页解码，
> 中文注释会变成乱码并直接破坏语法解析。改动这个文件后请确认 BOM 还在。

### 为什么扩展不做构建

扩展的逻辑不复杂（连桥、操作 DOM、探测状态），原生 JS 足够，
省掉一整套构建配置，改完刷新扩展就生效。

## 踩过的坑

以下每一条都是实机调试撞出来的，共同点是**都不会报错**——功能静默失效，
日志干干净净。改动相关代码前请先读这一节。

### 一、Windows 的前台权限：三处都栽在同一个机制上

Windows 只允许**拥有前台权限**的进程切换前台窗口。没有权限时
`SetForegroundWindow` 返回 false、什么也不做、不抛异常。这一条坑了三个地方：

1. **助手投递不了** —— 它是被主程序 spawn 的后台子进程，天生没有前台权限。
2. **输入条抢不到键盘** —— `win.focus()` 同样受限。窗口看着在最前面，
   打的字却全进了原来那个应用。
3. **抢到了又弄丢** —— 见下。

`ForceForeground` 因此是两级策略，顺序不能改：

- **先**直接 `SetForegroundWindow`。调用方本来就有权限时（比如刚响应完自己注册的
  全局快捷键）这一下就够了，且无副作用。
- **失败了**才动用 Alt 技巧：模拟一次 Alt 按下抬起，让系统以为本进程刚收到用户输入。

Alt 技巧并非免费：**单独的 Alt 会激活窗口菜单，可能把刚拿到的焦点又弄丢**。
早期版本无条件用它，结果输入条弹出来约 1 秒后就自己消失了。

还有个顺序问题：抢前台会重新激活窗口、冲掉 input 元素的焦点，
所以**必须等抢完前台，再通知渲染层聚焦输入框**（见 `focusAndNotify`）。

### 二、全局快捷键：注册成功 ≠ 能用

中文输入环境下可选组合极少，这些都已被占用：

| 组合 | 被谁占 |
|---|---|
| `Alt+Shift` | 系统切换输入语言 |
| `Ctrl+Shift` | 切换输入法 |
| `Ctrl+Space` | 切换中英文 |
| `Shift+Space` | 切换全角/半角 |
| `Alt+Space` | ChatGPT 桌面端自己的唤起键 |

两种失效方式都不报错：被输入法吃掉时 `register()` 照样返回 true 但收不到按键；
被别的程序占用时返回 false，而早期代码只在失败时打日志、没人看。

所以现在不硬编码单个快捷键，而是 `HOTKEY_CANDIDATES` 逐个试、用第一个成功的，
并把**实际生效**的那个显示在托盘菜单里。这台开发机上 `Ctrl+Alt+Space` 就是被占的，
实际跑的是 `Ctrl+Alt+J`。

### 三、MV3 扩展的两个致命特性

**service worker 空闲约 30 秒就被回收，内存状态全部清零。**
最初用一个内存 Map 记录「哪些标签页可用」，于是：页面上报 → SW 记下 → SW 休眠 →
记录蒸发 → 下次握手报「无可用目标」。现在一律用 `chrome.tabs.query` 现查，
无状态才可靠。

**`ws.ping()` 不能保活。** 协议层的 ping 由浏览器底层直接回 pong，
**不会触发 service worker 的事件循环**，所以它照样被回收、WebSocket 随之断开。
只有真正的 `message` 事件才能重置那个空闲计时器——所以心跳必须是应用层消息
（见协议里的 `heartbeat`）。

### 四、content script 不能用顶层 const

页面若在扩展安装/重载之前就打开着，里面是没有 content script 的，而且不会自动补上。
所以 background 会用 `scripting.executeScript` 补注入——**注入进的是同一个全局作用域**。

顶层 `const` 第二次声明直接抛 `Identifier has already been declared`，
整个脚本在第一行就作废。表现出来是一句毫无指向性的「页面脚本没有响应」，
而且刷新页面能好、一重载扩展又坏。

`adapters.js` 和 `content.js` 因此都包在 IIFE 里。幂等标志也要**注册成功后才置位**——
反过来的话，一旦注册中途抛异常，标志已经是 true，之后每次补注入都会跳过注册，
彻底卡死无法自愈。

### 五、`focusable: false` 会把鼠标点击一起挡掉

悬浮标窗口原本设了 `focusable: false`，本意是「别抢焦点，像贴纸一样待着」。
它在 Windows 上会加 `WS_EX_NOACTIVATE`，而实测**连鼠标点击也一并被挡住**——
胶囊上的按钮完全点不动，没有任何报错，渲染层日志干干净净，
点击事件压根没到达页面。

不进任务栏由 `skipTaskbar: true` 保证就够了，不需要 `focusable: false`。

### 六、鼠标穿透：`forward` 选项两头都会坑你

悬浮标窗口 216×110，而本体只占中间一小块，其余是透明区域。
不做穿透，那一大片看不见的地方会一直挡着桌面图标和下层窗口的点击。

`setIgnoreMouseEvents` 有两个独立的坑：

1. **`{ forward: true }` 承诺的「穿透时仍转发 mousemove」在 Windows 上收不到。**
   渲染层完全静默，于是「鼠标压到本体上就恢复可交互」这套逻辑根本没机会触发。
   最终改成**主进程轮询** `screen.getCursorScreenPoint()`（120ms 一次），
   渲染层只负责用 `ResizeObserver` 上报本体的矩形——因为展开成胶囊和收拢成小圆
   可命中的范围差一大圈。轮询不优雅但绝对可靠，也不依赖渲染层收得到事件。

2. **恢复可交互时不能再带 `{ forward: true }`。**
   那个选项只在 `ignore` 为 true 时有意义，跟 `ignore: false` 一起传会让这次调用
   **静默失效**——窗口永远穿透，胶囊按钮点不动，没有任何报错。
   排查时直接读窗口的 `WS_EX_TRANSPARENT` 位（`GetWindowLong(hwnd, -20) & 0x20`）
   比从现象倒推快得多。

### 七、窗口能变高，body 也得能变高

输入条展开提示词列表时会调 `setBounds` 加高，但 CSS 里
`body { height: 132px }` 写死了，于是窗口是变高了、内容却被裁在 132px 处，
表现为「列表只露出第一条」。**凡是会改尺寸的窗口，body 都不能写死高度。**

同一类问题还有一处：测量 `offsetHeight` 要等下一帧（`requestAnimationFrame`），
同步读到的是布局更新前的旧值，窗口会比内容矮一截。

反过来，这个窗口的 body **永远不该滚动**。伪玻璃那条路上 `.bar` 有 8px 外边距，
会把 body 的内容顶出去一丁点，窗口右边就冒出一条垂直滚动条，正压在圆角上。
要滚的是列表，那是 `.prompts` 自己的事，两层都给 `overflow: hidden` 封掉。

还有一条容易写错的：`INPUT_MIN_HEIGHT` 是**防塌**用的下限，不是「正常高度」。
它一旦顶到真实内容高度，就会把底边裁掉几像素，而日志里只会写
「117 → 116」这种看着像四舍五入的行，根本不像出了问题。

### 八、判断剪贴板变没变，只有序列号这一条路划算

Electron 没有剪贴板变更事件，只能轮询。但**轮询什么**决定了这功能能不能用：

- **比对 `readText()`**：抓不到「图片 A → 图片 B」。连按两次 Win+Shift+S 截图，
  文本始终是空的，于是被当成没变——而连续截两张图恰恰是最常见的用法。
- **每轮读图算哈希**：一张 4K 截图的位图约 30MB。每 700ms 做一次，
  这个常驻小工具会变成机器上最耗 CPU 的东西之一。

Windows 的 `GetClipboardSequenceNumber()` 在剪贴板内容一变时就自增，
而且**读它不需要打开剪贴板**，是真正零成本的。序号没动就直接返回，
一个字节的内容都不用碰。助手本来就常驻，加一条命令的代价几乎为零。

### 九、静默窗口必须包住整个 deliver，而且不能用布尔标志

投递时助手会**写两次剪贴板**：写投递文本、再恢复用户原本的备份。
两次都不是用户在复制，不排除的话每发一条消息，历史里就多一条自己刚发的内容。

两个都会让人栽的细节：

1. **必须包住整个 `deliver` 调用。** 恢复剪贴板是助手返回**之前**的最后一步
   （而且恢复前还 `Start-Sleep 50ms`），只圈住前半段等于没圈。
   收尾还得再多等一会儿，否则最后那次 `Set-Clipboard` 会被当成用户的新复制。
2. **不能用布尔标志。** 静默会嵌套，也会背靠背连着来——发完消息紧接着点
   「复制扩展连接密钥」。布尔标志在后一种情况下会被前一次的收尾提前清掉，
   于是密钥照样进了历史。必须是计数 + 可重排的收尾定时器。

### 十、别让调试工具骗了你

排查中一度以为 UI 被裁切，其实是**截图脚本没声明 DPI 感知**：系统缩放 125% 时
`GetWindowRect` 返回虚拟化后的 216 而非真实的 270，于是只截到左边 80%。
UI 一直是好的。任何用 Win32 API 量尺寸的脚本，都要先调 `SetProcessDPIAware()`。

同理，`PrintWindow` 抓不到 Chromium 的 GPU 合成内容（对话正文是黑的），
也抓不到 Windows 11 的任务栏托盘区——**抓不到不等于没有**。

### 十一、Win11 亚克力：三个都不报错的坑

**1. 它和 `transparent: true` 是互斥的，不是叠加的。**
Electron 文档只写了「Windows 11 22H2 and up」，没提这一条。
窗口带 alpha 通道时，DWM 画在它底下的 backdrop 根本透不上来，看到的还是一块纯色。
`backgroundColor` 也必须是全透明的 `#00000000`，否则窗口底色会严实地盖住 backdrop。
这两件事都不报错，只是「忙活半天还是一块纯色」。

**2. frameless 窗口拿不到 Win11 的自动圆角。**
改成不透明之后四个角是齐齐的直角，而这条路上 CSS 补不了——窗口本身不透明，
画出来的圆角只会让四角各露出一小块底色，比直接方角还难看。
只能 P/Invoke `DwmSetWindowAttribute(hwnd, 33, DWMWCP_ROUND)`，
走已有的 PowerShell 能力层加一条命令（`round-corners`）。

**3. 底色太薄会让文字读不出来。**
亚克力透出的是**下面那扇窗口**，不是壁纸。底下压着一张白底网页时，
整条会被顶成浅灰，上面的浅色文字直接糊掉；而且同一条上半截浅、下半截深，
因为上下压着的根本不是同一个东西。实测 `0.45` 就是这个下场，最后定在 `0.78`——
仍然看得出背景在动，但不论底下是什么，对比度都守得住。

### 十二、临时改窗口尺寸，会顺手毁掉用户拖出来的位置

庆祝动画要把悬浮标窗口撑大再缩回。两次 `setBounds` 都会触发 `moved`，
而 `moved` 上挂着 500ms 去抖的位置落盘——于是去抖会稳稳地把**撑大时**的坐标
存成「用户拖到的位置」。表现是悬浮标每庆祝一次就往左上挪一点，
下次开机在一个新地方，而且没有任何报错，只是一天天往角落里爬。

所以整个动画期间必须挂起位置保存，**而且要拦两道**：`moved` 的入口拦一次，
去抖回调的出口再拦一次。只拦入口的话，挂起之前就已经排进队列的那一发照样会落地。
缩回之后也不能立刻放开——刚才那次 `setBounds` 触发的 moved 还在队列里躺着。

还有两条一起栽：

- **`ResizeObserver` 盯不到这件事。** 它观察的是本体，而本体自始至终是 52×52，
  变的是窗口。漏掉 `window.addEventListener('resize', …)` 重报命中矩形的话，
  那两秒里鼠标命中判断整体偏移，表现为「庆祝的时候胶囊点不动」。
- **窗口贴着屏幕边时扩不动。** 悬浮标常年待在右下角，往外扩会直接出界。
  各边得独立算可扩展量，而扩出来的框就不再以本体为中心了——
  不把这个偏移补回去，本体会随窗口一起平移，看着像它自己蹦了一下再弹回来。

### 十三、粒子飞向圆心，会被圆心那个圆吞掉

第一版的汇聚动画让粒子从 48px 外一路飞到圆心。本体是个半径 26 的圆，
于是后半程粒子全在圆内部走，被圆的底色盖住——看起来像「粒子飞到一半凭空消失」。
让它们停在本体外沿（而不是圆心）才看得见汇拢。

同一处还有个几何问题：窗口不是正方形的。待机时 216×110，中心到左右有 108、
到上下只有 55，按圆形轨迹撒的话上下那两颗会贴着窗口边缘走甚至被裁掉，
轨迹得用椭圆。

### 十四、pnpm 的构建脚本审批字段换过两次名

装了 `electron-builder` 之后 `pnpm dev` 会直接退出，日志里只有一句
`Ignored build scripts: electron-winstaller`——看起来像某个包没装好，
实际是 pnpm 拒绝运行它的安装脚本，然后让整条 `install` 以 1 退出。

字段名随版本搬过两次：pnpm 10 在 `package.json` 的 `pnpm` 字段，
pnpm 11 挪到 `pnpm-workspace.yaml` 的 `onlyBuiltDependencies`，
**11.5 起改用 `allowBuilds`，且要逐个写 `true`/`false`**。
旧字段对已有依赖还兼容，所以 electron 和 esbuild 一直没事，
唯独新加的那个包卡住——很容易误判成是新包本身有问题。

`pnpm approve-builds` 是交互式的，在脚本或 CI 里用不了；直接改
`pnpm-workspace.yaml` 的 `allowBuilds` 即可。**别只删掉那段占位配置**，
pnpm 下次 install 会原样写回来。

## 已知限制

- **仅 Windows。** 能力层依赖 Win32 API 与 PowerShell。
- **目标应用收进托盘时投递会失败**，会提示"没找到目标窗口"——
  它需要一个可见窗口才能接收粘贴。这种时候文本会原样还给你（见上文）。
- **同时发给多个桌面端目标时，焦点会闪切好几次**，一个目标一次（各 200~400ms）。
  没有别的办法：那两个封闭应用只收前台窗口的键盘输入，而前台只有一个。
  全走网页端的话一次都不会闪。
- **投递会占用剪贴板。** 期间会临时写入并在结束后恢复，
  但只能恢复文本内容；如果原本剪贴板里是图片等格式，会丢失。
  这两次写入已被剪贴板历史的静默窗口排除，不会把你刚发的消息记进历史
  （「复制扩展连接密钥」同理）。
- **剪贴板历史不做内容过滤**，复制过的密码、验证码同样会被记下来。
  只靠 15 条上限自然挤掉，以及托盘菜单里的清空入口。
- **改完扩展代码必须在 `chrome://extensions` 点 ⟳ 重载**，
  已打开的页面由 background 自动补注入，不用手动刷新。
- **站点改版会让网页端失效。** 所有选择器集中在
  `apps/extension/src/adapters.js`，每项都留了多个候选，改那一个文件即可。
  失配时投递会返回页面实况（各类输入框的数量与可见性），据此改选择器即可，不用猜。
- **安装包没有代码签名**，首次运行 Windows SmartScreen 可能拦一下，属预期。

## 实测状态

三个目标都在真实环境下端到端验证过（Windows 11，缩放 125%）：

| 目标 | 投递 | 探测档位 | 结果 |
|---|---|---|---|
| ChatGPT Classic | 闪切粘贴 | `approximate`（UIA） | ✅ 蓝环 → 绿环 |
| Gemini 桌面端 | 闪切粘贴 | `coarse`（像素差分） | ✅ 蓝环 → 绿环 |
| ChatGPT 网页端 | 扩展操作 DOM | `exact`（读停止按钮） | ✅ thinking → done |

网页端还有个额外优势：走扩展的 `tabs.sendMessage`，**完全不抢焦点**，
标签页在后台也照收——连那 200~400ms 的闪切都省了。

**打包版**也实测过：独立启动（不经终端）、helper 从 `release\win-unpacked\resources\`
正确加载、UIA 探测正常、闲置收拢正常、投递成功。
0.2.0 的包又走了一遍：helper 仍从包内 `resources\` 加载且 BOM 完好，
日志落盘写着 `——— 启动 0.2.0 ———`（没有 dev 后缀），
网页端投递 → tabId 往返 → 跳转整条链路在打包版里一样跑通。

多目标、跳转、失败回填这三项的验证情况：

| 验的东西 | 怎么验的 | 结果 |
|---|---|---|
| 多轨聚合与分段圆环 | `XFB_DEMO=1` 走双轨四帧，截图看 | ✅ 一半绿一半蓝分段清晰；`approximate + coarse` 取到最低的 `coarse` |
| 网页端并行投递 | `XFB_SELFTEST=chatgpt-web,gemini-web` | ✅ 两条 deliver 连着发出，不互相等待 |
| 部分失败不回填 | 同上（一个成一个败） | ✅ 没弹输入条，整体仍算 done |
| 全部失败回填文本 | `XFB_SELFTEST=gemini-web`（扩展未连） | ✅ `[输入条] 投递失败，文本已交还（15 字）`，输入条重新弹出 |
| 网页端跳转整条链路 | `tools/fake-extension.js` 接管桥，回报一个编出来的 tabId | ✅ tabId 原样带回，`[跳转] → 标签页 424242：成功` |
| **桌面端双目标串行** | 打包版 `XFB_SELFTEST=chatgpt-desktop,gemini-desktop` | ✅ 两次投递相差 554ms（排队，不是并行），两轨都进入 `coarse` 探测 |
| **桌面端失败回填** | 打包版投给收在托盘里的 ChatGPT Classic | ✅ `没找到目标窗口，可能应用没启动或被收进了托盘`，文本原样还回 |

假扩展那一项可以自己跑：

```bash
XFB_SELFTEST=gemini-web XFB_REVEAL=1 pnpm dev   # 一个终端
node tools/fake-extension.js                     # 另一个终端
```

它值得说一句：用真扩展验跳转会把测试消息真的发进自己的对话里，
而这条链路要验的是「tabId 有没有原样存下来、完成后会不会拿它发 activate」，
跟页面里到底发了什么没关系。

桌面端那两项是在真实环境里跑的：测的时候 ChatGPT Classic 恰好收在托盘里，
正好是〈已知限制〉里写明会失败的那种情况——以前它会让人白打一整段。
新版 ChatGPT 桌面端实测降级到了 `coarse`（UIA 没唤醒），和上面表里写的「UIA，失败则降级」一致。

**还没验的**：桌面端的跳转（走 helper 的 `focus`，和输入条抢焦点同一条命令，天天在跑）、
面板里的 Ctrl+点击多选（纯渲染层交互，需要亲手点）。

## 打包

```bash
pnpm dist     # 编译 + 打成安装包
```

`dist` 自带一次 `build`，不能只跑 `electron-builder`：改完代码直接打包的话，
进包的是 `out/` 里上一次编译的产物，装出来一个「看着是新版、行为是旧版」的东西，
而且没有任何提示。

产物在 `apps/desktop/release/`：`XuanFuBiao-<版本>-setup.exe`（约 77 MB）。
装完开始菜单里就有「悬浮标」，双击即用——**不再需要终端，也不依赖源码和 Node**。
开机自启在托盘菜单里，默认关闭。

> ⚠️ **打包后必须实机验证一次投递**，不能只看 dev 跑得通。
> 最容易漏的是 `extraResources`：helper 脚本和托盘图标漏了的话，
> 程序照样能启动、界面照样正常，只有投递时才瘫，而 dev 模式完全掩盖这个问题。
> 快速判据：看进程列表里 `win32-helper.ps1` 的路径是不是指向
> `release\win-unpacked\resources\`，以及该文件首字节是否仍为 `EF BB BF`。

国内网络打包时工具链下载会卡，**先挂镜像再跑 `pnpm dist`**。
这台机器上就是 PowerShell，别照抄 bash 的 `export`：

```powershell
$env:ELECTRON_MIRROR = "https://npmmirror.com/mirrors/electron/"
$env:ELECTRON_BUILDER_BINARIES_MIRROR = "https://npmmirror.com/mirrors/electron-builder-binaries/"
pnpm dist
```

bash / Git Bash 下则是：

```bash
export ELECTRON_MIRROR="https://npmmirror.com/mirrors/electron/"
export ELECTRON_BUILDER_BINARIES_MIRROR="https://npmmirror.com/mirrors/electron-builder-binaries/"
```

不挂镜像时的表现值得记一笔：它**不是立刻失败**，而是停在

```
• packaging  platform=win32 arch=x64 electron=33.4.11
```

一动不动**整整十分钟**，然后才报 `Timeout awaiting 'request' for 600000ms`。
中途看起来完全像卡死，很容易等不及就去查别的地方。
镜像没写进 `dist` 脚本里，是因为镜像域名换过（`npm.taobao.org` → `npmmirror.com`），
写死在脚本里下次失效时更难查。
